## 三、视频：怎么跑通的（最有价值的一节）

### 3.1 真实契约（用户提供的可运行脚本，非文档推断）

同一台网关主机，**`/api/` 前缀，不在 `/v1` 下**：

```
提交  POST {root}/api/seedance/createVideo
      {"model","content":[{"type":"text","text":…}],"resolution","ratio","duration","generate_audio"}
      → {"id":"cgt-YYYYMMDDHHMMSS-xxxxx"}

轮询  POST {root}/api/seedance/getVideoResult   ← POST 带 body，不是 GET
      {"id","model"}                            ← model 每次都要重发
      → {"status","content":{"video_url"},"error"}
      终态：succeeded / failed / cancelled / expired，其余继续等

取消  DELETE {root}/api/seedance/task/{id}?model=…   ← id 在路径，model 在 query
```

### 3.2 为什么必须是新驱动而不是给 `ark-task` 加参数

除了上面三处路由差异，还有一条**会毁掉画面**的：Ark 把生成选项拼进提示词文本（`--resolution 480p --dur 5`），这个网关用普通 JSON 字段。**把 Ark 那套装饰过的提示词发过去，`--flag` 会变成画面内容**。有测试钉死提示词里不出现 `--`。

### 3.3 不硬编码内网主机（接续者别改坏这一点）

目录条目**不能**按 `litellm-internal` 匹配——那是某家公司的内网地址，不该进产品。走既有通道：`resolveMediaModelSpec` 本就支持「用户显式声明的 `media_endpoint` 盖过内置目录」。用户在 设置 → 模型 → 某模型 里把 `media_endpoint` 填成 `seedance-gateway` 即可，同时保留目录对 seedance 参数面的既有知识。有两条测试钉死。

### 3.4 探测方法论（下次遇到"某个 API 到底通不通"直接复用）

对候选路径 POST **故意不合法的请求体**：路径已路由 → 返回带真实信息的 4xx（校验就挡住了，**不建任务不扣费**）；未路由 → 200 空 body。

**必须带对照组**，这是 08-06 那次判断失误的根源：

- 正对照：一条已知能用的路径（`/v1/chat/completions`）
- **负对照：一条肯定不存在的路径**（`/v1/zzz-not-a-real-endpoint-9f3a`）——没有它，"200 空"无法归因

⚠️ **我自己在这上面又栽了一次**：拿到负对照后我写下「nginx 只代理 `/v1/`，其余落静态」，但我明明探过 `/api/v3/…` 和 `/api/openapi.json` 且都拿到 200 空，却把它们归进「未路由」而没继续在 `/api/` 命名空间里探——**真实入口就在那里**。判据是对的，是我把结论的覆盖面自己缩窄了。**教训：判据成立 ≠ 你搜过的范围足够。**

## 四、入口设计：一个选择器回答一个问题（本日最后一个决定，**别改回去**）

用户问「图片和视频生成的入口到底在哪」「我在会话框里看不到这些模型」——这是同一个问题的两面。

**改之前的状态**：入口是发送框工具行里一个写着「对话」的按钮（点开才有图片/视频生成）；媒体模型只在 设置 → 能力扩展 → 工具 里配。于是用户在设置里把模型标成「视频模型」，**却在会话里再也找不到它**——标签像是白标了；而那个按钮没有任何迹象表明背后有生成模式。

**根因**：存在**两个平行的模型概念**（聊天模型在选择器里、媒体模型在设置里），而用户只被告知了一个。

**决定**（用户在三个方案里选的）：媒体模型并回模型选择器，分三组——

```
<provider 名>     ← 聊天模型（原有分组）
图片生成          ← isMediaGenSupported('image', …) 为真的
视频生成          ← isMediaGenSupported('video', …) 为真的
```

**语义**：选中媒体模型**不设置聊天模型**（对它们发 chat 请求必 404），而是把发送框切进对应生成模式并使用该模型；选回聊天模型则**退出**生成模式——否则就是一个能进不能出的入口。

**为什么用 `isMediaGenSupported()`**：设置页、执行路径、这个选择器共用同一个谓词，所以「选择器里能选的」和「运行时能跑的」不会漂移。**接续者若要加筛选逻辑，改这个函数，别在选择器里另写一套。**

**⚠️ 跨组件通信的坑**：选择器在会话头部、模式 state 在发送框（`useMediaComposer`），两者是**不同平台外壳挂载的兄弟节点**。走 `mediaModeStore` 这个极小的外部 store（原本单向：发送框 → 头部 pill；本轮改双向）。**请求带 `seq` 且只应用一次**——没有它，用户手动切回对话后的任意一次重渲染都会把旧请求重新应用，等于跟用户抢发送框的控制权。

**已验证**（真机）：三个分组齐全且聊天组里没有媒体模型；点视频模型 → 模式/chip/预估/placeholder/退出按钮全部就位；点回聊天模型 → 回到对话态。
**未验证**：媒体模型在下拉里的**选中勾选标记**（代码里有 `activeMediaId`，但 CDP 没匹配上 Arco 的标记方式）。

### 6.1 两个列表分叉导致"选中了不能聊天的模型"

### 9.7 ⚠️ 切走再切回，送框会被拽回已退出的生成模式（第三会话，已修）

模型选择器把「切进图片/视频模式」作为带 `seq` 的 request 写进 `mediaModeStore`，送框订阅并应用，靠 `useRef` 记住最后应用过的 seq 以免重复应用。守卫失效于两件事凑在一起：**`requests` 这个 Map 只写不删**（`clearMediaModeSnapshot` 卸载时只清了 `snapshots`），而 **`useRef` 跟着组件实例一起死**。

送框一旦卸载重挂（切到别的会话再切回、HMR 重载），ref 归零而早已应用过的 request 还在 store 里 → 旧请求被第二次应用。用户视角：选了视频模型 → 手动退出生成模式 → 切走再切回 → **送框自己又跳回视频模式**。这正是 §4 那段注释声称要防止的「跟用户抢送框控制权」，只是 `seq` 防住了重渲染、没防住重新挂载。

已修：request 是一次性指令，新增 `consumeMediaModeRequest`，应用完即消费；**按 `seq` 匹配后再删**，使 effect 运行与消费之间新到的请求不会被误删（否则会静默吞掉用户最近一次选择）。`673c9e3d2`。

⚠️ **这个缺陷卡在测试的缝里**：`mediaModeStore.dom.test.ts` 本有 11 条，覆盖 seq 递增、会话隔离、卸载清理，**唯独没有一条问「应用之后请求还在不在」**。补的 4 条里，remount 回归按真实方式建模（卸载旧 hook、新建订阅），并**做了负向验证**——把 `requests.delete` 临时注释掉重跑，确认正是那两条关键用例失败。

13. **⚠️ 写含 Windows 路径的文档，当心不可见控制字符。** 本文一度把 dev 的 userData 目录写成 `%APPDATA%one-Dev`、把探针目录写成 `D:ionui-m0`——看着像"漏打了一个字符"，实际是文件里躺着**字节 `0x01` 和 `0x07`**：路径经过某层正则/shell 替换时，`\1` 被当成捕获组引用、`\a` 被当成响铃符**吃掉并替换成了真的控制字符**。`grep` 打印出来毫无异样，只有 `cat -A`（显示 `^A`/`^G`）或按字节 `count(b'\x01')` 才看得见。**照着这种路径去找目录，永远找不到**——而第 9 条恰恰是在教人"先确认 userData 目录"。写 Windows 路径优先用正斜杠（`D:/aionui-m0`，本仓其他文档都这么写，一处没中招），或写完用 `grep -c $'\x01'` 扫一遍。
14. **shell 里嵌套引号做批量替换会静默失败——必须 read-back 验证。** 修上面那条时，`python -c "…"` 报告 `replaced 5`，但文件字节纹丝未动（多层引号里 `\\\\` 的实际落值与预期不符）。**脚本自己报告"改了 N 处"不是证据，改完重新读回来数一遍才是。** 复杂替换直接写成 `.py` 文件用绝对路径跑，别塞进 `-c` 的引号里。
15. **一次性指令要真的消费掉，别只靠 `useRef` 记"已处理"。** ref 跟着组件实例一起死，而模块级 store 里的数据不死——组件一重挂载，"已处理"的记忆没了、待处理的数据还在，于是又处理一遍（§9.7）。**凡是"只应做一次"的跨组件消息，删除它才是幂等，记住它不是。**
16. **"设置键早于新架构"是这条线的第三类系统性缺口。** 前两类是「上游前端合了、后端没合」（§1）和「会话内做了、欢迎页没做」（§9.8）；这一类是**旧设置键还在被下游当作唯一真相**（§9.9）——产品早就改用 `model_kind` 声明，而读取方仍只认 `tools.*GenerationModel`。**遇到"用户明明配了却说没配"，先查读取方认的是不是上一代的键。**
