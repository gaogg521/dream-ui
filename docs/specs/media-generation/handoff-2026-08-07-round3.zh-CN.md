## 2. 第 ③ 项：多图 —— 结论被实测推翻过一次，别再走回头路

round2 §5 写的是「`ark-seedream` 的 `maxN: 1` 低报了模型能力，改大概率直接可用」。**这个判断是错的**，我按它改成 9 之后，
用真实端点验了三件事：

- 方舟 `/api/v3/images/generations` 对 `doubao-seedream-5-0-pro-260628` **直接忽略 `n`**：`n: 2` 和 `n: 99` 都只回一张，
  `usage.generated_images` 也是 1；
- 它的组图参数被显式拒绝：`sequential_image_generation is not supported by the current model`。
  ⚠️ 我第一次是拿**非法枚举值**探的，怀疑报错文案误导，又用合法取值（`auto` + `max_images: 2`）重试了一次，**同样报错**——字段确实不支持；
- 同一条链路上网关的 `gpt-image-2` 则**真的认 `n`**，`n: 2` 回 2 条。

所以 `maxN` 的语义是「**一次请求回几张**」，不是「最多能要几张」。把它调大只会让界面出现一个点了不算数的计数器。

**落地形态**：在适配器之上扇出（`executeMediaGeneration` 的 `fanOut`），要 N 张就发到 N 张为止。几个花钱的细节都有测试钉住：

- 末轮只要余数（要 9 张、一次 4 张是 `4+4+1` 而不是 `4+4+4`，否则白多三张还照付）；
- 失败即止，已出的照常返回；
- 每轮之间查 `signal.aborted`，所以取消是真的少花钱；
- `MAX_IMAGE_FAN_OUT = 9` 由代码钉死——**这条路 agent 经 MCP 工具也走得到**，不能让它一次要 500 张；
- 扇出后把 `n` 从 `droppedParams` 里摘掉，否则等于教 agent「别再要多张」。

只做图片且只做同步形态：Form C 一个 job 只有一个远端 task id，拆开会让重启续跑不知道在等哪个。

**真机实证**：方舟 seedream `n=2` → 两张落盘、md5 与大小均不同（是两次独立生成，不是同一张存两遍），
计费上报 `count=2` 未漏计。

## 3. 第 ⑤ 项：图生图 —— 真实契约（用户提供，已用本应用 key 复验）

之前图生图 400，报错是 Go 的 JSON 解析错误，**看着像请求体畸形，实际是路由错了**。真实契约：

```
POST https://litellm-internal.123u.com/api/seedream/v1/images/generations
Content-Type: application/json
Authorization: Bearer <key>

{"model":"doubao-seedream-5-0-pro","prompt":"...","size":"1K",
 "output_format":"png","watermark":false,"stream":false,
 "image":"data:image/jpeg;base64,..."}
```

两处结构性差异（**都不是 OpenAI 协议能表达的**）：

1. **路由在 `/api/seedream/v1/` 下，不在 `/v1/` 下。** 拿 seedream 模型打 `/v1/images/generations` 会被回
   `404 model "…" not found`——模型确实没挂在那儿。这和 seedance 视频的 `/api/seedance/*` 是同一个套路，
   应该是该网关给厂商原生 API 做的命名空间。
2. **参考图是 JSON body 里的 data-URI，字段名 `image`，走同一条 generations 路由。** 没有 `/images/edits` 这条路由可接 multipart。

⚠️ **已用本应用自己的 provider key（`8e4a…`）复验通过**，不需要用户测试台那把 key；那把 key 我没写进任何代码或提交。

**落地形态**：新增 `adapters/seedreamGateway.ts` + 目录里新增一类**同步** endpoint style。

- 关键点：`media_endpoint` 此前隐含「异步任务 API」，命中就强制 `form: 'C'`。同步 style 必须**先**判、且**不能**被改成 Form C——
  否则会变成一个等 task id 的轮询 job，而网关根本不发 task id，只会挂到超时。为此新增 `SYNC_IMAGE_ENDPOINT_STYLES`。
- ⚠️ **写测试时抓到的真集成缺口**：内置目录的 `ark-seedream`（`/seedream/i`）会先命中，把用户声明整个盖掉，
  所以 `resolveMediaModelSpec` 里「目录命中后仍尊重显式选择」那段也必须处理同步 style，
  并且要**替换**而不是继承 params——内置条目描述的是方舟直连的像素尺寸（`1024x1024`），这个网关不认，
  照搬就等于把一个会被拒的值摆给用户选。该网关的尺寸词表是 `1K/2K/4K`。
- 模型设置里的 endpoint 下拉此前只列异步那批，`seedream-gateway` 根本选不到，已按模型类型分开给
  （图片才列同步 style；视频不列，列了就是给一个用不了的选项）。

**未做**：真机跑一次图生图。契约本身已 curl 验过 200，但没走完「应用内选参考图 → 出图 → 卡片渲染」。

## 4. 第 ⑥ 项：浏览器里发起/取消生成

WebUI 里能看到 job 列表了（round2 补的），但**发起和取消仍走的是同一条死桥**——浏览器没有 Electron IPC，
`ipcBridge.media.startJob` 在那边解析不到任何东西。表现是：送框能显示生成模式和预估花费，点发送什么也不发生。

**落地形态**：`/media/jobs` 加 `POST`（发起）、新增 `/media/jobs/cancel`（取消）；渲染层三个调用点统一改走
`mediaJobsTransport` 的 `startMediaJob` / `cancelMediaJob`。主进程侧把发起/取消收进 `mediaBridge.mediaJobRouteDeps()`，
HTTP 与 IPC **共用同一份实现**（原本两处接线各自内联了一份 listJobs/subscribeJobs，已一并收敛）。

### ⚠️ 安全面：必须知道的一条实测事实

这条路由**会花钱**，而且它和只读文件路由一样，绕开了 `/api/*` → aioncore 的鉴权。为判断这是不是我新开的门，我实测了：

```
curl -o /dev/null -w "%{http_code}" http://127.0.0.1:25809/api/conversations   # → 200，无任何凭据
```

**即：通过 WebUI 端口访问后端接口面，当前配置下本来就没有会话闸门**（包括所有能驱动 agent、因而会花钱的接口）。
所以新增的发起路由**与现状同级，不是新开一道门**——但这也意味着「WebUI 可达性」本身就是信任边界。
接手者若要收紧，应当收紧的是 WebUI 那一层，而不是单独给这条路由加一把锁（那只会给人一种已经锁上的错觉）。

已做的收敛：body 读取有 32MB 上限（参考图 data-URI 会很大，所以不能定得更紧），畸形 body 直接 400 不往下传，
`GET /media/jobs` 仍然只是列表——方法闸门有测试钉住，**负向验证过**：去掉它之后 GET 会挂在等 body 上，两条列表测试转红。

### 9.4 浏览器发起 / 取消（第 ⑥ 项）——真机通过

全部从 **LAN 地址** `http://<lan-ip>:25809` 发起，不是环回：

- `POST /media/jobs` → 建作业 → 轮询到 `done` → 落盘；

- WebUI 送框整条链路：「对话模式」→「图片生成」→ 输入 → 发送 → 新建会话 → 卡片实时显示「已提交/生成中/取消」→ 完成后**缩略图真的渲染出来**（`<img>` `naturalWidth=1024`，src 是 `/media/file?path=...` 而非 `one-media://`），卡片带复制 / 引用到输入框 / **下载** / 重新生成 / 花费 ≈$0.02。

这一次同时把 round2 的 ①（网页端加载媒体）和 ②（远程模式「打开所在目录」→「下载」）也验了：卡片上那颗按钮显示的就是「下载」。

**先回答 §6 第 5 条要求的那个前置问题：这不是 dev 造成的。** 证据链四条，全部读的是代码或实测：

1. `packages/web-host` **自己没有任何鉴权**，`/api/*` 原样反代给 aioncore（`static-server.ts` 顶部注释明写「All auth goes to backend's aionui-auth crate」）；
2. `backend-launcher.ts:637` **无条件** `local: true` → 恒传 `--local`，**不分 dev / 打包**；
3. `aionui-auth/middleware.rs:63-79`：local 模式下**永不返回 401**，没有 token 就注入 `system_default_user`（机主身份，带管理员角色）；
4. `allowRemote` 打开时 WebUI 绑 **0.0.0.0**（本机实测 25809 就绑在 0.0.0.0，后端 61253 只在 127.0.0.1）。

四条叠起来的实测后果（**全部从 LAN 地址、零凭据**）：

```
GET  /api/conversations        → 200，返回全部真实会话
GET  /api/providers            → 200，返回 provider 的 **明文 api_key**
POST /media/jobs               → 建作业成功（会花钱）
```

**前端有登录页，后端没有闸门。** 浏览器打开会跳 `#/login`（账号密码 + 飞书），但那只是渲染层路由；攻击者不需要登录，直接打 API 即可。

⚠️ **还有一处比 `/api/conversations` 更糟的**：`/api/webui/{reset-password,change-password,change-username,generate-qr-token}` 这组端点在 `routes.rs:179` 注释里写的是「local-only, enforced inside each handler」，但 `ensure_local_mode(state.local)` 检查的是**进程 flag**，不是**调用方是不是本机**——全仓 grep 不到任何 `ConnectInfo` / `is_loopback` / peer-address 校验。我用 `GET` 打这三条 POST 路由，从 LAN 拿到的是 **405**（说明路由可达、没被鉴权拦下），即从 LAN `POST /api/webui/reset-password` 大概率能重置机主的 WebUI 密码并在响应里拿到新密码。**我没有真的 POST**——那会改掉你的密码。这一条需要你自己验或授权我验。

**推荐方案（A）：把闸门从「进程 flag」改成「连接来源」。** 在 aioncore 取 `ConnectInfo<SocketAddr>`：peer 是环回 → 保持现在的 operator 回落（桌面端免登录不变）；peer 非环回 → 走完整 JWT 校验（WebUI 登录这才真正生效）。同一改动顺带堵住上面那组 `/api/webui/*`。

- 收在正确的层：`/api/*` 一大片和 `/media/*` 一起被覆盖，不会出现「只锁了媒体、其余照样敞着」的错觉；
- **不能只把 `local` 改成 `false`**：桌面端渲染层不发 token（middleware 注释明写），那样会把桌面端自己打成 401。

**备选（B）**：在 `packages/web-host` 反代层要求会话凭据。纯 TS、改动小，但它得回头问后端「这个 token 有效吗」，等于在代理层再实现一遍鉴权，且后端仍然是敞的（任何能直连后端端口的进程照样免鉴权）。

**代价（两个方案共有）**：所有远程 WebUI 用户从此必须真的登录才能用——现在很可能有人是「打开就能用」的。所以这一条动手前要你确认。

## 10. WebUI 鉴权缺口修复（2026-08-07 第四轮，用户拍板方案 A）

**这一节不属于媒体线**，但它是媒体线那条会花钱的 HTTP 路由暴露出来的，所以记在一起。

### 10.1 缺陷

见 §9.6。一句话：`--local` 回答的是「**进程**是不是本机启动的」，而需要回答的是「**这个调用方**是不是机主」。
桌面端恒传 `--local`，WebUI 又把同一个后端挂到 `0.0.0.0`，于是局域网上任何人零凭据就是机主。

### 10.2 为什么不能直接取 ConnectInfo（原推荐方案的机制被实测推翻）

我一开始的建议是「在 aioncore 取 `ConnectInfo<SocketAddr>`，peer 非环回就要求 JWT」。**行不通**：
`static-server.ts` 的用户侧监听是 `net.createServer`，它把连接**裸 TCP splice** 给内部 http server 或后端，
所以后端看到的 peer **恒为 127.0.0.1**——远程和本地在那一层长得一模一样。

**真正知道来源的是代理本身**，所以改成由它告诉后端。

### 10.3 落地形态

| 层                                    | 改动                                                                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `static-server.ts` `forwardToBackend` | 给每个转发给后端的请求**设置**（非追加）`x-aionui-forwarded-origin: webui`                                                                    |
| `static-server.ts` `stampProxyOrigin` | `/ws` 与 `/api/stt/stream` 是裸 splice、不经 `forwardToBackend`，改为把该头**插进请求头字节**（插在请求行之后，因而排在客户端任何同名头之前） |
| `aionui-auth/middleware.rs`           | `auth_middleware` 的 operator 回落改为 `state.local && !is_webui_proxied(...)`；带标记的请求落到严格分支，无有效 session 即 401               |
| `aionui-auth/routes.rs`               | 把原 `api_public` 拆成「真·公开」(`/api/auth/status`) 与 `api_local_only`，后者整组加 `reject_webui_proxied_middleware` → 403                 |
| `static-server.ts` extraHandlers 前   | `/media/*` 不经后端，**自己不做 JWT 校验**，而是拿调用方凭据去问后端 `/api/auth/user`（唯一事实源仍在后端），失败即 401                       |

**信任模型**：后端只绑环回，所以伪造这个头需要已经能在这台机器上跑代码；且该头只会让检查**更严**，
代理是无条件**覆盖**写入的，远程调用方无法把它去掉。

⚠️ **不能简单地把 `local` 改成 `false`**：桌面端渲染层不发 token（middleware 注释明写），那样会把桌面端自己打成 401。

### 10.4 ⚠️ 我自己引入又当场抓回来的一个回归（这一条最值得记）

第一版 `/media/*` 闸门是**每个请求都去探一次** `/api/auth/user`。真机一开会话就露馅：
浏览器里 `/media/jobs` 回 **401**，而 `/api/auth/user` 回 **429**——那个端点在 API 限流器后面，
一页结果有多少张图就打多少次探测，**把用户自己的限流额度打爆**，然后我的 fail-closed 把 429 翻译成
「401，你的图没了」，受害者是一个**正常登录了的**用户。

已改为按凭据缓存 5 秒（`SESSION_PROBE_TTL_MS`），一次 burst 只探一次；正负结果都缓存
（只缓存正结果的话，无凭据的洪水照样能打爆后端）。TTL 同时界定了「会话被吊销后还能用多久」。

**教训：把一个受限流保护的端点当作鉴权探针，等于把别人的额度当成自己的。**
单测覆盖不到它——mock 后端不限流。这是真机点开一个会话才出现的。

## 11. 修复之后的自查（起了一个审计 agent，**它报的 6 条我逐条自己验过**）

用户在收尾阶段要求「顺便查查还有没有别的 BUG」。结论先说：**审计揪出了两个我自己引入的严重缺陷**（都已修），
另有两条属实的既有缺陷（未修），**一条它报成 CRITICAL 的其实不成立**。

⚠️ **方法论**：子 agent 的报告是线索不是事实。这一轮 6 条里有 1 条的核心论断是错的（见 11.4），
而它错的方式恰好是最典型的那种——**下否定断言时 grep 的是自己猜的名字**。

### 11.1 【我引入的 · 已修】`/media/*` 闸门把登录页本身也锁了

第一版把闸门写成「**这个 server 配了** extraHandlers 就要会话」，而不是「**这个请求是给** extraHandlers 的」。
两个桌面调用点都是无条件传 `extraHandlers` 的，于是 `/`、`/index.html`、`/assets/*` 全部 401。

**后果是死锁**：登录 UI 就在那个 bundle 里，拿不到会话是因为拿不到那个页面，而拿不到那个页面是因为没有会话。
匿名实测四条全 401 坐实。

修法：新增 `StaticServerOptions.sessionGuardedPrefixes`，由**宿主**声明哪些前缀要会话（桌面端传 `['/media/']`），
web-host 依旧不认识业务路由。已补回归测试：匿名取 `/`、`/index.html`、`/assets/main.js`、`/chat/123` 必须 200，
而 `/media/file` 必须 401。

### 11.2 【我引入的 · 已修】标记是按连接打的，后端是按请求判的 —— 可被流水线走私绕过

`stampProxyOrigin` 只改 splice 首包。一个 TCP 连接上流水线发两个请求：

```
GET /ws HTTP/1.1\r\nHost: h\r\n\r\nGET /api/providers HTTP/1.1\r\nHost: h\r\n\r\n
```

第一个匹配升级路由、被打标记（400，连接不关）；**第二个未打标记直达后端**，吃到 local 模式的机主回落。
**真机实测拿到了 200 和明文 `api_key`**——等于整套修复被绕过。

根因一句话：**标记的粒度是连接，鉴权的粒度是请求，两层对「信任单位」的理解不一致。**

修法：升级路径单独走 `spliceUpgradeToBackend`——请求头之后还有字节就直接断开（真实升级没有 body 也不流水线）、
101 之前不转发客户端任何字节、上游没回 101 就在转发完拒绝响应后关闭连接。真机复验：同一载荷现在什么也拿不到，
而正常 WebSocket 握手仍然 `readyState=1`。

### 11.3 【既有 · 未修 · 已读码确认】`workspaceDir` 由调用方指定，且会变成文件读取的允许根

`mediaJob/index.ts` 的 `const workspaceDir = input.workspaceDir?.trim() || fallbackWorkspaceDir();` **不做任何校验**，
而 `mediaHttpRoute.ts` 的 `listAllowedRoots` 正是把各作业的 workspace 收集起来当围栏根。
即：能建作业的人 `POST /media/jobs {"workspaceDir":"C:\\"}`，之后就能用 `/media/file` 读该盘下任意图片/视频
（扩展名白名单仍在，所以限于媒体类型）。

围栏本身是好的（`path.relative` 而非字符串前缀、target 与 root 都过 `realpath`、软链逃逸会被拒），
**问题不在围栏，在根的来源是调用方可控的数据**。

收紧鉴权后这条需要有效会话才能触发（此前是完全匿名），但对已登录的远程成员依然成立。**未修，留给下一轮。**

### 11.4 ⚠️ 【报成 CRITICAL，实际不成立】office 代理不是任意端口 SSRF

审计称 `/api/office-watch-proxy/{port}` 的 port 直接来自路径、无白名单，可打本机任意端口。
**我实测打不通**：任意端口一律 **403**。读码确认存在校验——
`aionui-office/src/proxy.rs:66,79` 的 `is_active_port` / `is_active_watch_port`，
失败即 `ProxyError::PortNotActive` → Forbidden。

它之所以下错结论，是因为 grep 的是 `allowed_ports` / `is_managed` 这些**它自己猜的名字**，
没搜到就断言「没有白名单」。真实机制叫 `PortNotActive`。

属实的部分只有「这个 router 确实没挂 auth_middleware」，但它能到达的只有 office 预览自己注册过的活动端口。

### 11.5 【既有 · 未修 · 交给你判断】

- `/api/providers` **明文返回 api_key**，而且这是被测试**主动锁死**的行为
  （`aionui-api-types/src/provider.rs` 的 `test_provider_response_api_key_plaintext` 断言不含 `***`）。
  收紧鉴权后它不再匿名可读，但对企业部署里任何**已登录的普通成员**依然可读。要改的话得先改那条测试。
- `--local` 时 **CSRF 中间件整个不挂**（`router/routes.rs:639-646`），而桌面端恒传 `--local`。
  会话 cookie 是 `SameSite=Lax`，跨站 POST 打不进来，所以**审计没能给出可用的利用链**，
  它自己也标注了「未枚举有副作用的 GET 端点」。属于同一个 `local` 语义混用的遗留，**未验证是否可利用**。

### 11.6 这一轮真正该记住的一条

**两个严重缺陷都是我自己在「修安全问题」的过程中引入的**，而且都**不是单测能发现的**：
一个要匿名开浏览器才看得见（我自己的浏览器一直带着 cookie），一个要手写 TCP 流水线载荷。

**给安全闸门写测试时，必须显式构造「没有凭据的那一侧」和「协议层的畸形输入」**——
只测「有凭据能过、无凭据被挡」这两条，恰好会漏掉「无凭据的人连登录页都打不开」和「有人根本不走你以为的那条路」。

## 13. §12.2 中两条已按用户拍板处理（2026-08-07 收尾）

### 13.1 `workspaceDir` 不再能把任意目录变成可读根（1oneUI `35464a30c`）

**判断过程比结论重要**，因为第一直觉的修法是错的：

- ❌ **不能只放行「已登记的资产文件」**——作业记录会被清理（终态超期 + 上限 500 条），
  那样老会话的图会变成裂图。
- ❌ **不能在建作业时校验 `workspaceDir`**——「生成物落进你选的工作目录」是刻意做的功能，
  而主进程无从判断哪些目录是用户真的选过的。

**落地形态**：根只保留**应用工作目录**（会话产物恒在其下，所以记录被清理后照样可读），
目录之外改成按**作业已登记的资产文件逐个精确放行**。用户选的项目目录里的产物照常可读，
而编造的 workspace 什么也换不到——目录不是这个路由产出过的文件。

**真机验证（已登录会话，不花钱）**：往一个**已是作业 workspace 的目录**里放一个非资产文件——

负向验证：把精确匹配换回目录匹配，「不让已登记文件授权它的邻居」那条立刻转红。

### 13.2 provider 的 `api_key` 只给机主（1oneCore `da7a66d1`）

用户定的边界：**明文本身没问题，但只能自己可见，企业其他成员不可见**。

⚠️ **`providers` 表没有归属列**（部署级全局），所以做不了「按 owner 过滤」。判据改成「是不是机主」：
请求没经过 WebUI 代理（本机桌面端直连自己的后端），或经代理但会话解析出的就是机主账号。

⚠️ **动手前核实过一件会推翻方案的事**：媒体生成要用 `api_key`，而它取 provider 走的是
`httpRequest` → `getBaseUrl()`，看着会指向远端。实测不会——`enterpriseMode` 用 `localStorage`，
**主进程里没有**，所以 `isEnterpriseRemoteActive()` 在主进程恒为 false，取的始终是本机后端直连。
**掩码不会打断生成**，包括企业客户端模式。

`CurrentUser` 取成 `Option` 是因为本 crate 的测试刻意不挂鉴权中间件；经代理却解析不出身份时
按「不是机主」处理（fail closed），既有 22 条测试原样通过。create/update 的响应一并掩码。
