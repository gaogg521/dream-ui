### 原始条目（存档，按严重度排序）

### D1【架构级·最重要】瘦客户端路由与「离线下发」互相矛盾

**证据**：`httpBridge.ts getBaseUrl()`——客户端模式下**一切**默认请求（含会话/agent/技能列表）路由到远端服务器；仅 `preferLocalBackend` 端点打本地。
**后果**：

- 客户端模式成员的 agent **在远端服务器上跑**：本地物化的团队技能/MCP 在线时**不被消费**（远端会话读远端盘）。
- 服务器挂了 → 成员**完全不能工作**（聊天本身就是远端的），「服务器挂了不影响使用」的承诺在客户端模式下**不成立**——只有成员切回单机模式才能用上已物化的团队资源（笨拙但可行的逃生通道）。
  **建议（需拍板）**：改为**混合路由**——成员的 agent/会话在**本地** aioncore 跑（吃本地物化的团队技能/MCP，天然离线），仅 组织/治理/注册表/协作看板（oneOrg/oneAdmin/oneDevops）走远端。这与「管理员定义→下发落地→成员本地消费」的产品模型完全自洽，也是本审计**最优先建议**。工程量：改 `getBaseUrl` 的路由策略 + 会话链路验证，中等偏大。

### D2【高】退出企业不清理已下发资源

**证据**：`OverviewTab.tsx` 的 `oneOrg.exit` 只调后端退出；本地 `team-skills/`（含 auto_active）与团队 MCP 连接器无任何清理；`isEnterprise` 变 false 后同步停止但**已物化内容永久残留**。
**后果**：离职/退出成员的 agent 继续自动加载企业技能、继续连企业 MCP 端点——**离职带走能力 + 残留指令注入**。
**修法**（小工程，建议尽快）：exit 成功后调用本地 `team-sync`（空集 + authoritative）+ `mcp/team-sync`（空集 + authoritative）清空两类物化资源。

### D3【高】多租户共库泄漏面

**证据**：`one_skill_registry`/`one_requirements` 等 one-devops 表**无 tenant_id**（001_init.sql）；`tenant_of` 仅用于派发。一台服务器若存在多个租户（`oneOrg.create`/邀请并未强制单租户），所有租户**共享全部注册表与看板**。
**修法**：短期在 `oneOrg.create` 强制「一服务器一企业」（已有租户则拒绝）；长期表加 tenant_id。

### D4【中】邀请码熵不足

**证据**：`generate_invite_code` 4 字节 → 8 hex（2^32）。接口在登录门后（缓解），但企业内任意登录用户可在线枚举他人租户邀请码（配合 D3 危害升级）。
**修法**：8 字节 + 尝试速率限制/失败锁定。

### D5【中】带凭据的团队 MCP 无法真正下发

**证据**：fork registry 只存 `endpoint`+`hasKeys` 标志，**无凭据存储**；物化后带鉴权的 MCP（sse headers / stdio env）连不上。
**修法**：凭据信封加密下发，或服务端 MCP 代理（成员连服务器、服务器持凭据转发）。产品决策项。

### D6【中】协作动作无审计

**证据**：one-org 审计仅覆盖管理员动作；注册表写（现在是管理员行为=策略变更！）、需求派发、breakdown 均无审计记录。
**修法**：registry 写 + dispatch 接入 one-org 审计管道。

### D7【低】团队技能同名遮蔽

同名 last-wins（含遮蔽内置技能）。F1 修复后仅管理员可触发，风险可控；建议 registry 名称唯一约束 + 下发端冲突提示（MCP 侧已有个人冲突保护，技能侧无）。
