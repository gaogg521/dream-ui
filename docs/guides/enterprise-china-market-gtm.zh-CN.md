## 一、一句话结论

产品的功能面已经不薄，**卡住的是交付形态和数据安全，不是功能数量**。

所谓"服务器模式"目前是**某台员工的 Windows 电脑当服务器**。任何有 IT 部门的
公司，这一条就走不进采购流程——不是嫌功能少，是根本不进流程。这把客单价锁死
在几万块，且只能卖给老板自己拍板的小团队。

**在补掉交付形态之前，做再多功能都不会改变能签什么单。**

## 三、五个真正卡签单的缺口

### ① 交付形态（最致命）

现状：客户端/服务器状态机是"哪台机器建了企业，哪台就是服务器"。
企业 IT 要的是：Linux 服务器、内网私有化、Docker 或离线安装包、备份、高可用。

`one-platform` 的容器化目前是 `Noop` stub（probe 返回 `not_configured`），
属于**预留而非实现**。

> **这一条不解决，后面所有功能都不产生商业价值。** 它也不是一个功能，是一次
> 形态改造：后端要能脱离 Electron 独立跑、要有独立的部署与升级路径。

### ② 数据安全侧是空的

现有的企业管控是"花了多少钱、能用哪个模型"——**财务视角**。
企业安全部门问的是**内容视角**：

- 员工把合同、代码、客户名单发给外部大模型，怎么拦？→ 现在拦不了。
- 事后能不能查谁发过什么？→ 查不到。agent 审计只记录 **tool call**
  （`one-org/service.rs` 的 `list_agent_audit` 从 `messages` 表捞
  `type IN ('tool_call','acp_tool_call')`），**没有会话内容**。

这是国内企业采购 AI 工具的**第一个问题**，不是第三个。

### ③ 企业无法统一下发模型渠道

`one-devops` 只有三个下发通道：`one_skill_registry` / `one_mcp_registry` /
`one_rag_documents`。**没有 provider registry。**

后果：每个员工必须自己拿到并粘贴模型 API key（图片/视频尤其贵）。企业采购最
不能接受这个形态——key 分发即失控、离职即泄漏、无法按部门切换渠道、无法统一
议价。

> ✅ 已解决（2026-08-08）。设计与落地见 §六。

### ④ 组织与人事流程没闭环

有 SSO（飞书/钉钉/企微/LDAP/OIDC），但**没有通讯录自动同步**：飞书/钉钉的
组织架构进不来，部门树要手工维护。1000 人的公司没人会维护它。

> ⚠️ **原文这里还写着「离职资源接管也还没做」，那句是错的**（2026-08-09 读
> 代码核实）。`transfer_ownership`（1oneCore `one-devops/service.rs:548`）早
> 就有，前端 `UsersTab.tsx` 的移除流程也已经是「转移资源 → 移除成员 →
> 释放席位」的完整闭环。**缺的从来不是接管机制，是没人知道谁离职了**——而这
> 正好是通讯录同步要解决的另一半。
>
> ✅ 通讯录同步（飞书）+ 离职检测已于 2026-08-09 落地，见 §六-3。

### ⑤ 商业化机制只有一半

License 离线激活（Ed25519 签名码）做得不错，但缺：POC/试用期、席位到期提醒、
渠道分销、开票、SLA。另外国内企业不接受"订阅 + token"双重计费，要的是包年
包量的资源包。

## 四、差异化：现在讲错了

竞品——钉钉 AI、飞书智能伙伴、扣子企业版、字节 HiAgent、阿里百炼、腾讯元器、
智谱/月之暗面企业版——**全是云端**。跟它们比"我也有 AI 助手"必输：生态、模型、
价格都打不过。

这个产品唯一打不烂的差异化是两条：

> **数据不出内网 + 桌面端能真正碰到员工本机的文件和工具**

云端 SaaS 结构上做不到第二条。252 个专家 + 数字员工 + 定时任务 + 团队作战 +
图片视频，合起来应该讲成 **"能在内网里真干活的 AI 员工工作台"**，而不是
"企业版聊天助手"。

图片/视频能力恰好强化这个叙事：市场部在内网批量出图出片、素材不出内网、有
预算管控和留痕。但 §五 的那些缺口正好把这个卖点逐条打折。

## 五、图片/视频与企业版的打通情况（2026-08-08 逐条核对）

### 已经打通

- 成本上限 + 模型 allowlist：`startMediaJob` 是 MCP 与发送框两条路的唯一漏斗，
  precheck 在建 job 之前。
- 用量进 `one_usage_events`，与聊天共用同一个 budget rollup 和用量看板。
- 媒体按张/按秒独立计价（不按 token），用户自填单价优先于内置费率表。
- api_key 不再下发 MCP 子进程；企业内非机主看到掩码。
- 个人版红线：无企业 → 直接放行、零额外请求。

### 本轮修掉的三个真缺口

| 缺口                                                                                                                                                                                                           | 修法                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **客户端模式下整套管控空转**：`/api/one/billing` 不是 governance 路径，precheck/用量打的是员工本机 aioncore，而成员资格只存在于服务器 → `resolve_enterprise_id` 恒为 `None` → 一律放行、用量写进没人看的本地库 | 抽出 `process/services/governanceEndpoint.ts`（原来只服务团队知识库），媒体管控改走它；同时把 `/api/one/billing` 加进 `GOVERNANCE_PATH_PREFIXES`，企业后台的订阅与用量页也不再读本机空表 |
| **数字员工 / 定时任务 / 团队 / 存量会话用不了媒体**：后端两个 agent 工厂都有 `if !selected \|\| row.builtin { continue }`，内置 MCP 只能靠前端 `withBuiltinMediaMcp` 写进会话快照，而它只挂在新建会话页        | 新建 `factory/session_mcp.rs` 收口两个工厂共用的选择规则；媒体这一个内置 MCP 跟着自己的 `enabled` 走，与前端同一条规则。**刻意只放这一个**，否则每个 agent 都会拿到 PDF 导出与团队知识库 |
| **审计看不见媒体**：`list_agent_audit` 的 detail 只抽 command/path/url，不抽 prompt；发送框直发那条路不产生任何 message                                                                                        | detail 补 `$.args.prompt` / `$.input.prompt`；用量上报补 `conversationId`                                                                                                                |

### ⚠️ 真机验证抓出来的两个后续缺陷（都已修）

单测全绿、代码看着对，但真机跑一遍才暴露：

1. **agent 发起的生成，账本里仍然 `conv=None`。** 原因写在 `startMediaJob` 自己的
   注释里——"渲染层知道自己的会话，MCP 调用方不知道"。媒体 MCP 是 stdio 子进程，
   除 env 无从得知服务哪个会话，于是**最常见的那条路恰好是留不下踪迹的那条**。
   修法：照 `AIONUI_MEDIA_WORKSPACE_DIR` 加 `AIONUI_MEDIA_CONVERSATION_ID`。
2. **走 repo 行进会话时，媒体 env 一个都没注入。** 媒体 env 的注入原本只写在
   _快照_ 路径，而本轮 `session_mcp` 修复让媒体 MCP 是以 **repo 行**身份进会话的。
   后果是工具能用但两件事都丢：产物落兜底目录、用量归因为空。⚠️ 我一开始把
   "图片落在 `%APPDATA%` 而不是会话工作目录"归因于"agent 没传 workspace_dir"，
   **同一个根因，我第一次判断错了**。两个工厂的 repo 行路径各补一次注入。

**教训**：给一条既有能力开一条新的到达路径时，要顺着那条新路径把**沿途所有
per-conversation 上下文**都数一遍——旧路径上"顺手就有"的东西，新路径上一件都
不会自动跟过来，而且缺了不报错。

### 仍未打通（未列入本轮）

- **生成物是纯本机文件**：`media-jobs.json` 在 userData，产物落工作目录，不进
  会话 schema、不进备份、不进知识库、不跨端、无项目组可见性。企业里"谁生成了
  什么"没有一处集中账本。
- ~~**allowlist 是一张表，媒体和聊天共用**~~ → ✅ 2026-08-08 已改为可操作。共用
  是刻意的（避免两套互不知情的规则），所以修的不是拆表，而是**让失败有出口**：
  拒绝时点名哪个模型、去哪加、以及"这份清单同时管聊天和图片视频"；输入框也补了
  同样说明并把占位符加上媒体模型。真机验过。
- **precheck 传输失败即放行**（fail-open，代码注释写明是刻意的）。桌面端本地
  执行，本身也不是强边界。
- **未知模型计价为 0**（⚠️ 仍未真正解决，只是不再无声）：内置费率表按模型名匹配，
  网关自定义名（很常见）落进 0，**媒体等于对预算免费**——上限对那个模型悄悄失效。
  已加 warn 让它可诊断，并用测试把"仍为 0"钉死。**刻意不发明兜底费率**：那会改变
  管理员的上限实际拦什么，属定价决策，需要你拍板。可选项：①给未知媒体模型一个
  保守非 0 底价；②在用量看板上把"N 笔无费率"显式标出来逼管理员填单价；
  ③维持现状，靠 warn + 文档。
- **无 AIGC 标识**，且 `seedreamGateway.ts` 硬编码 `watermark: false` 主动关掉
  上游水印。→ 见 §八。

## 六、企业统一下发模型渠道（已落地并真机验证）

> **2026-08-08 用户拍板**：走**服务器代理**（api_key 只在服务器解密、永不出服务器），
> 作用域**企业级、可按项目组覆盖**。下面是最终设计，不是草案。
>
> **Stage A（服务端）与 Stage B（客户端）均已完成并通过真机端到端验证**，见本节末三节。

**目标**：管理员在企业后台配好聊天/图片/视频渠道，成员开箱即用，**员工全程
接触不到 api_key**。

**放哪**：`one-devops`。三个既有 registry 已带 `scope`/`team_id`/`visibility`
（迁移 009），新增 `one_provider_registry` 与它们同构，`member_visibility_where()`
与 `validate_resource_scope()` 原样复用。加密不构成割裂——`encrypt_string` /
`decrypt_string` 在 `aionui-common`（基础层），任何 crate 都能用，key 照
`ProviderService` 的既有方式从 `data_secret` 派生后注入。

**代理为什么是路径透传而不是协议感知**：`aionui-codex-bridge` 是协议感知的
（解成 `LlmEvent` 再重编码）。媒体一家就说三种互不兼容的形状（Form A
`/v1/images/generations`、Form B chat、Form C 的 DashScope/Ark 异步任务 API），
协议感知要为每种写一遍，且厂商加第四种就崩。改为把 channel id 之后的路径原样转发：

```
ANY /api/one/model-proxy/{channel_id}/{*path}
  → {upstream_base_url}/{path}，注入真实 Authorization
```

于是下游**零改动**全部工作：聊天、Form A、Form C 拼出的路径原样抵达。

**成员端凭据是专用可撤销 channel token，不是会话 JWT**：JWT 会因加入/退出/移除
成员而轮换（one-org 刻意为之），用它会让每次成员变动打断所有已配渠道，直到下次
同步。专用 token 与 JWT 生命周期解耦、离职一条语句全撤、并在代理端天然带上
per-member 归因（正是 T4 内容审计要的）。**只存哈希**。

**关键约束**：

1. **key 永不下发到成员机器**。⚠️ 直接下发明文 key 等于把问题从"每人一把"换成
   "每人拿到公司那把"，**更糟**。这是设计上最容易做错的一步，已用测试锁死。
2. 与现有 `providers` 表并存：个人自配的渠道不受影响，企业下发的标为只读。
3. 个人版红线：无企业配置时零额外请求、行为零变化。
4. 与 §五 的媒体链路对齐：媒体模型走同一个下发通道。

### 已落地（Stage A，服务端）

| 内容                                                                                                                                                                    | 位置                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 迁移 `one_provider_registry` + `one_provider_channel_tokens`                                                                                                            | `one-devops/migrations/010_provider_registry.sql`                          |

端到端那 4 条起一个假厂商服务器、走真实 axum 路由，验的是设计赌注本身：
**三种协议形状（chat / images / DashScope 异步任务）的路径原样抵达**、
**成员的 channel token 被换成公司凭据且自己不外泄**、无效 token 根本到不了厂商、
撤销后立即在代理这一层被拦。⚠️ 凭据替换那条做过**负向验证**（删掉注入那一行，
正是它失败）。

### 真机验证（2026-08-08，重编内嵌后）

**模型渠道端到端全过**：迁移 010/041 在真实 dev 库干净应用 → 建渠道 → 列表逐字节
搜不到真实 key（命中 0）→ 签发 token → **三种协议形状路径原样抵达假厂商，且
Authorization 是公司凭据而非成员令牌** → 无/伪造/Basic 三种 auth 全 401 且根本
没到厂商 → 停用后立刻 401 → 编辑不带 key 时凭据仍在 → 成员端物化出
`managed_by=enterprise` 的 provider 且个人 provider 未被动 → 托管行 update/delete
均 400、个人行 200 → authoritative 空同步清托管留个人 → 环境清回原状。

⚠️ **上游刻意用本地假厂商而非真实 key**：真实厂商只能告诉你"成功了"，分不清
"它转发的是公司凭据"还是"它把我的令牌透了出去"——而那正是唯一要验的那件事。

**媒体链路全过**：在一个按 cron/数字员工形态（无前端快照）建的会话里，注入结果
是 `["aionui-image-generation","ftshare","stock-sdk","team-search"]`——媒体在，
而**同为 builtin+enabled 的 `one-export-pdf` 与 `one-team-knowledge` 不在**（实证
"刻意只放这一个"真的成立）；agent 真的调用工具并出图，`media-precheck 200` 命中。

**已补真机 CDP 点检（2026-08-08）**：后台页六列/新增/编辑/密钥不回显（编辑时密钥框
为空、占位符「留空则保留原有密钥」、整个弹窗里搜不到密钥）/改名不带 key 后凭据仍在，
以及成员端「企业下发」标签。⚠️ **点检当场抓到一个真错**：托管行的编辑删除入口
其实一直可点——`hidden` 与 `flex` 同写在一个 className 里不生效（同为单类选择器，
UnoCSS 输出 `.flex` 在 `.hidden` 之后，源序 flex 赢）。已改为条件渲染。
**且排查时差点被自己骗过**：数 `querySelectorAll` 的按钮个数会给出假绿，
`display:none` 的元素照样匹配选择器——判据必须是 `offsetParent` +
`getBoundingClientRect` + computed display。

## 六-2、T4 会话级内容审计 + 基础 DLP（2026-08-08 落地）

安全部门问的第一个问题是内容问题——员工把什么粘进了模型，事后查不查得到。
此前企业侧的管控全是财务性的（花了多少、能用哪个模型），这一块是空的。

### 判定放在成员机器上，不放服务器

要检查的是提示词，而提示词是在成员自己那台机器上组装的。放服务器只有两条路，
两条都不成立：

- **每次发送往返一次服务器**——在产品最热的路径上加延迟，且公司服务器一断，
  策略就失效（而且是静默失效）。
- **只检查走公司模型代理的流量**——正好漏掉最值得抓的那种：把合同粘进自己
  配的个人模型里。

所以形态是：规则在企业后台编写 → 下发到成员机器 → 本地判定 → 命中记录回传。
下发与回传复用技能/MCP/模型渠道那条同步链路（同一个 5 分钟定时器）。

### 三条刻意的产品决定

| 决定                                                   | 为什么                                                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 新规则默认**只记录不拦截**                             | 还没看清真实命中率就开始拦，误报会把人推去用浏览器粘贴，比原本要防的泄漏更糟                                                               |
| 审计表存的是**掩码后的摘录**，永不存命中值             | 一张把全公司身份证号汇总起来的表，自己就成了这套部署里最值钱的目标                                                                         |
| 成员取规则的接口**不做可见性过滤**                     | 判定在成员机器上跑，一条他取不到的规则就是一条不生效的规则                                                                                 |
| 被拦下时**必须告诉成员是哪条规则**，并用他自己的语言说 | 一个只看到"Forbidden."、不知道为什么发不出去的人，下一步就是打开浏览器粘贴过去——正是这个功能要防的那件事。与"新规则默认只记录"是同一个考量 |

⚠️ **第四条是真机验证抓出来的，不是设计时就有的**（2026-08-08）。第一版用了
`ApiError::Forbidden`，而它的 `public_message()` 刻意把 message 抹成裸
`"Forbidden."`（防泄漏沙箱路径等内部信息，`error.rs` 里有测试锁死）——扫描器
一直生成着正确的句子，丢失发生在 HTTP 边界上，单测照不出来。同一个吞噬也压着
P1-2 的预算与 allowlist 拒绝，一并修了。现在三处拒绝共用
`aionui_conversation::PolicyDenial`：稳定 `code` + 英文兜底 + 参数（规则名、
模型名），前端按 code 渲染 13 语言文案、拿不到参数才回落英文。
⚠️ **只有已知的策略变体走可见文案**——内部错误（DB 出错之类）仍然只说
"策略无法校验"，闸门照旧 fail closed。在 message 被抹掉的年代这不重要，
一旦文案要给人看，`e.to_string()` 就会把 SQL 和路径送到界面上。

### 两条必须写在脸上的边界

- **这不是对付"能控制自己机器的成员"的防线。** 决心要绕的人可以停掉同步、
  改二进制、开浏览器。它抓的是意外粘贴，并留下记录。当成硬安全边界，就是在
  宣称架构给不了的保证。
- **规则内容会落到成员机器上。** 而规则本身可能就是敏感的（客户名、项目代号）。
  这是相对"每次发送往返服务器"权衡后的选择。若将来判定不可接受，退路是
  「本地判 + 规则只存哈希」，代价是只能全词匹配、没法用正则。

### 已知缺口（不是疏漏）

- **只检查消息正文，不扫附件**——那要在发送路径上读并解码每个附件。
- **延迟一个同步周期**：新规则最多几分钟后才开始应用，命中最多几分钟后才出现
  在后台。这正是"不做每次往返"换来的。
- **应用刚启动、首次同步完成之前的那几条消息不经检查。**

### 落地位置

| 层                                                     | 位置                                                              |
| ------------------------------------------------------ | ----------------------------------------------------------------- |
| 扫描器（关键词/正则/5 个内置模式，含校验位与数字边界） | `1oneCore` `aionui-common/src/dlp.rs`                             |
| 规则与命中的存储、CRUD、下发、上报                     | `1oneCore` `one-devops`（迁移 011 + `dlp_service.rs` + 4 个端点） |
| 本机规则缓存与命中缓冲                                 | `1oneCore` `aionui-system/src/content_inspection.rs`              |
| 接入发送路径（排在计费闸门**之前**）                   | `1oneCore` `aionui-conversation::ContentInspector`                |
| 下行/上行同步                                          | `1oneUI` `teamSkillSync.ts::syncContentInspection`                |
| 企业后台（规则 + 命中同屏）                            | `1oneUI` `ContentInspectionTab.tsx`                               |

⚠️ 排在计费闸门之前是刻意的：预算拦下的消息同样是人真的敲进去并按了发送，
正是要记的那个事件；反过来会让一家公司预算用完之后**悄悄停止收集内容证据**。

## 六-3、T6 通讯录同步 + 离职检测（2026-08-09 落地，全部四阶段）

在此之前，组织数据只在**某个人登录的那一刻、只针对那一个人**进来
（`one-sso/service.rs` 的 profile 刷新），而且 `org_unit_path` 存的不是路径、
是第一个部门的名字。这对"给成员打个标签"够用，对 200 人客户真正要的两件事
毫无用处：**免手工维护组织架构**，和**知道谁离职了**——后者恰恰无法由"人出现
时才有的数据"回答，因为离职的人正是不再出现的那个。

### 三条刻意的产品决定

| 决定                      | 为什么                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 只做飞书，钉钉/企微留接口 | 飞书是唯一有应用级 token + Contact API + `base_url` 可指向 mock 的；另两个 URL 是写死的绝对常量，无法验证。写了也只能说"编译过"，不能说"验过"                            |
| 离职**只检测不自动执行**  | 移除会轮换 JWT、撤销令牌、转移资源，全部不可逆。上游 API 抖一次就会批量误删人。后台只出建议列表，处置仍走成员页既有的移除对话框                                          |
| 通讯录人员**不写席位表**  | `one_enterprise_members` 是计费口径（`SELECT COUNT(*)` 就是账单）。1000 人的通讯录写进去会当场占满席位。镜像是"IdP 说有这些人"，与"谁绑定了本地账号并占一个席位"是两件事 |

### 一条不变量撑起整个功能的安全性

**`complete`：拉取有没有全部完成。** 下游"从通讯录消失"就是离职判定，而据此
行动会注销一个人的访问权。**一次半截的拉取——某一页 500 了、token 中途过期
——长得和"全公司一夜之间辞职"一模一样。**

所以任何一页失败都让整次拉取变成 incomplete（而不是返回更短的列表），存储侧
拒绝据此得出任何离职结论，后台对 partial 状态显示警告横幅而不是一个令人安心
的空表。这条做过负向验证：把"出错返回已拿到的部分"改回去，正是那条测试失败。

⚠️ 另一半信号：**飞书把离职的人留在通讯录里打标记，不是删掉**，所以还要读
`is_resigned`；同时**刻意不读** `is_activated`——那是还没入职的新人，当成离职
会在人家第一天就把号注销了。

### 运行位置

`cmd_server` 就是每台桌面端都在跑的那个二进制，所以调度循环**不能无条件启动**，
否则每个成员的笔记本都会去打公司的飞书应用，而且各自把通讯录写进自己本地库里
——那地方永远不会有人看。闸门是「**本机库里有没有启用的飞书配置 + 有没有企业**」：
客户端模式下 SSO 配置在服务器上，本地表是空的，循环每次 tick 就是两条便宜查询。
三条测试把这个钉死。

### ✅ wire 形状已用真实飞书租户验证（2026-08-09）

飞书的 list 端点**在此之前代码里不存在，仓库也没有抓包样本**，形状是照公开
文档写的。wiremock 测试当时只证明了**分页/去重/错误传播这些逻辑对**，证明不了
飞书真的按这个形状返回。

填入真实 `appId`/`appSecret` 后触发一次真实同步，`lastStatus=ok`：**250 个部门、
755 人，`complete=true`，无错误**。抽样核对了返回数据本身（不只是"没报错"）：
部门名是真实组织架构（"研发技术中心"、"财经部"…）、人员是真实姓名与岗位
（"张志玲/HRBP"…）、`externalIdField=union_id` 拉出来的 id 确实是 `on_` 前缀
——与飞书 union_id 的真实格式一致，说明字段映射猜对了。**形状假设成立，无需
校正。**

dev 可用 `AIONUI_FEISHU_BASE_URL` 把拉取指向替身服务器；**刻意做成环境变量而非
存储配置**——`parse_feishu_config` 把 `base_url` 挡在管理员可编辑配置之外是有意
的，把它变成可保存设置等于让"公司凭据发往哪里"变成一次 API 调用能改的事。

### 落地位置

| ------------------------------------------ | ------------------------------------------------------------------------------- |
| 飞书批量拉取（分页 / 单次运行 token 缓存） | `1oneCore` `one-sso/src/providers/feishu.rs` + `directory.rs`                   |
| 公司级镜像与对账、离职标记                 | `1oneCore` `one-enterprise`（迁移 `enterprise_003_directory` + `directory.rs`） |

| 企业后台「通讯录」页                       | `1oneUI` `DirectoryTab.tsx`                                                     |

### 阶段二（2026-08-09 同日落地）：离职列表接上既有的移除流程

阶段一只把人列出来，处置得自己走到「项目组 → 成员」再找一遍。这一步把两端接上，
但**接的过程中发现两层作用域根本对不上**，这才是本阶段真正的内容：

**离职列表是企业级的，移除是项目组级的。** 后端 `OrgService::remove_member`
作用于**调用者当前激活的项目组**，不在该组的人直接拒绝；资源接管还额外要求接收人
也在同一个组。而企业可以有多个项目组，企业管理员甚至可能一个都没加入
（`create_tenant_for_enterprise` 建的是空组）。**照直接线只会得到一个 400 和一个
仍然占着席位的人。**

所以做了三件事，而不是只加一个按钮：

| 改动                                                          | 为什么                                                                                                                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 离职行带上**此人所在的项目组**（`DepartedMemberDto.tenants`） | 前端得先知道能不能在这儿完成，才谈得上给按钮。缺这条信息就只能盲发请求                                                                                                 |
| **移出企业时注销其会话与凭据**                                | 此前 `EnterpriseService::remove_member` 只删席位行——被移出企业的人照旧登着、企业模型渠道令牌照旧能用。对"一个项目组都没加入"的人来说这是唯一的移除路径，它必须自己就够 |
| 移除对话框抽成共用组件，两个入口同一份实现                    | 复制一份必然漂移，而漂移的那一半正是转移→移除→释放席位的顺序                                                                                                           |

对话框据此分两态：此人**在管理员当前项目组内**→走完整流程（转移资源 → 移除成员
→ 释放席位）；**不在**→只释放席位并注销访问权限，并**点名他还在哪些组**，告诉
管理员接管要去哪做，而不是发一个注定失败的请求。

⚠️ **刻意不做的两件事**：没有「一键全部处理」（上游抖一次就批量误删人，与阶段一
的 `complete` 不变量同一条理由）；**没有新造"跨项目组移除"的权力**——那会让一个
企业管理员能删掉自己从未加入的组里的人，爆炸半径远大于本阶段的收益。

跨层用 `one_enterprise::SessionRevoker` trait + `aionui-app` 里的 adapter 委托
`OrgService`（同层不能直接依赖，照 `EnterpriseSync` / `CredentialRevoker` 的既有
安排）。「移出企业必须注销凭据」和「不在当前组时不得发项目组请求」两条都做过
负向验证，并在隔离实例上用真实二进制跑通：离职列表带出三种形态（在本组 / 在别的组
/ 无组）、移除后席位从 4 降到 3 且该用户 `jwt_secret` 被轮换、被拒的移除不动任何凭据。

### 阶段三（2026-08-09 同日落地）：部门树映射进项目组

管理员在项目组的「组织架构」页选一个通讯录部门当根节点，它和它下面的所有子
部门一次性映射进本项目组的部门树；可重复点，用来对账上游后续的组织架构变化。

**两个已知障碍怎么解的**：

- **`delete_department` 在有子部门/有成员时拒绝删除**——没有绕过它，而是直接
  复用：对账阶段把"从通讯录消失"的映射部门丢给这个既有函数，它拒绝就说明
  这个部门下面还挂着真实本地数据（手工加的子部门或分配的成员），报告给管理员
  而不是强删；它同意删才真的删。**免得为了这个功能重新发明一套"能不能删"的
  判断，抄错任何一个条件都是数据丢失风险。**
- **没有改父节点的 API**——新增 `PUT .../departments/{id}/parent`（含环检测：
  新父节点不能是自己或自己的后代）。这不仅解决了映射同步内部"上游部门挪了
  地方"时原地更新而非删了重建（删了重建会丢成员的部门分配），也是一个通用的
  管理员能力，只是这一轮没做拖拽 UI，仅留 API。

**三条不变量**（照抄 `aionui-system::managed_provider` 的既有安排）：只创建/
更新/删除自己拥有的行（`source='directory'`）、按外部 id 匹配保证重跑不重复、
删除范围限定在这次对账认定的集合内。**映射的根节点在本地永远是顶层部门**，
不管它在上游自己的父节点是谁——只映射一个分支不该把分支以上的结构也拉进来。

后端：`one-org` 新增 `map_directory_subtree`/`set_department_parent`，
`one_departments` 加 `source`/`directory_external_id` 两列；`one-enterprise`
新增 `list_directory_departments` 读接口；跨层走 `one_org::DirectoryTreeSource`
trait，但**没有**塞进 `OrgService` 的构造函数——因为 `one_enterprise_service`
在 `aionui-app` 里构造得比 `one_org_service` 晚（它反过来要用 `one_org_service`
撤销离职者会话），塞进构造函数会形成构造顺序死循环。改用 `OneOrgRouterState`
级别的桥接（照抄已有的 `company_resolver` 那条路——它也是这么解决同款问题的）。

**⚠️ 真机验证抓出一个单测没覆盖到的真缺陷，已修**：在真实开发库上映射了一个
真实部门后，再映射另一个完全不相关的部门——第一个被判定为"已从这次映射的
子树消失"，直接删掉了。根因是对账阶段的"existing"查询只按
`tenant_id + source='directory'` 过滤，等于把**整个项目组所有映射过的部门**
都当成"这次映射的责任范围"，而不是只对账"这个根节点自己映射出来的那些"。
两次独立的映射操作互相踩踏。修法=新增 `directory_map_root_external_id` 列，
记录每一行是哪次映射（哪个根节点）创建的，对账查询按这一列再收窄一层；
顺带补了一个此前没想到的边界——两次映射的子树有重叠（比如先映射"总公司"、
再单独映射"总公司"下的"研发中心"）会撞唯一索引，改为映射前显式检测冲突
并报错，而不是让原始的 SQL 约束错误直接抛出来。

**测试**：one-org 51 绿（+11，含新发现的"两次独立映射互不影响"、"子树重叠
时拒绝"，以及"重跑不重复"、"手工部门永不触碰"、"有本地数据的行保留不强删"、
"环检测"）、one-enterprise 28 绿（+1）。三条负向验证：去掉
`source='directory'` 过滤（结果发现这条本身是冗余保护，真正兜底的是
`directory_external_id IS NOT NULL` 的判断，双重保险）；绕过
`delete_department` 直接裸删（确认"保留有数据的行"测试真的会红——用户和
部门数据当场消失）；真机复现"两次映射互相踩踏"的原始缺陷后再验证修复。

**阶段四**（席位缺陷修复）已完成，见 §六-4。

## 六-4、超席位缺陷已修复（2026-08-09 落地）

不是 T6 引入的，但曾经在它的爆炸半径里（通讯录同步正是会把公司推过席位
上限的东西）。原链条逐环核实过：

超限 → `one-enterprise` 的 `reject_if_seat_full` 返回 `SeatLimitExceeded`
→ `EnterpriseSyncAdapter` 只 `warn!` 然后吞掉（`aionui-app/router/routes.rs`）
→ 该用户**没有企业成员行** → `resolve_enterprise_id` 返回 `None`
→ `check_send_allowed` 第一行就 `Ok(())` 放行（`one-billing/service.rs`）。

**后果：Free 档（3 席）的公司里第 4 个人开始，allowlist、成本上限、功能门控
全部对他失效。**

### 呈现形态：允许登录，标记待分配席位（不拒绝登录）

两个候选里选了"允许登录但标为待分配席位"，没有再问一遍——原因：

- **直接拒绝登录**意味着一次成功的企业 SSO 认证（身份是真的）却连应用界面
  都进不去，管理员事后也查不到"谁被卡住了"，只能等这个人来投诉。
- **允许登录但标记待分配**：这个人能看到界面，但每一次发送都会被明确拒绝
  并告知原因；管理员在后台成员列表和订阅页都能直接看到"几个人在等席位"，
  不必等投诉。

代价是要把"公司成员"和"占用的计费席位"拆成两个概念，而不是一个布尔。

### 怎么做的

新增 `one_enterprise_members.seat_status`（`enterprise_004_seat_status`
迁移，`'active'` / `'pending'`，默认 `active` 保证存量数据不受影响）：

| 环节                                                               | 改动                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sync_member`（登录时）                                            | 满员时**不再吞掉**——新成员照样写入一行，只是 `seat_status='pending'`。已是 active 的成员**永不重新评估**（后续降档不会连带驱逐正在用的人）；pending 成员**每次登录都重新判定**，这是唯一的"晋升"机制——没有单独的"分配席位"管理员按钮，全靠"再登录一次" |
| 席位计数（`reject_if_seat_full`/`can_add_seat`/`plan.seatUsed`）   | 只算 `active`，pending 不占用、也不会让 `can_add_seat` 永久卡死                                                                                                                                                                                        |
| `resolve_enterprise_id`（one-billing）                             | **不改**——pending 成员的行必须能被找到，`None` 的语义是"个人用户，跳过所有检查"，绝不能把 pending 也塞进这个语义，那就是把这个 bug 原样修复回来                                                                                                        |
| `check_send_allowed`/`check_model_allowed`（one-billing 治理入口） | 新增 `has_active_seat` 前置检查，pending 直接拒绝——**在看 allowlist/预算之前**，因为没有任何一份公司未设置的清单应该默认放行一个没有座位的人                                                                                                           |
| `check_media_allowed`                                              | 直接委托 `check_send_allowed`，自动获得同样的保护                                                                                                                                                                                                      |

⚠️ **关键不变量**：pending 成员必须"能被找到但被拒绝"，不能是"找不到从而被当成
个人版放行"——这正是原缺陷的根因，修复必须避免用同一种失败模式把自己绕回去。

前端：企业后台「成员」列表新增席位标签（已分配/待分配席位）；「订阅与用量」
页在有人等待时显示警告横幅并点出人数；发送被拒时展示专门文案（区别于预算
超限/模型不在清单内，因为解法不同——前者要等预算窗口，这个要等空出席位或
升级套餐）。13 语言。

**测试**：one-enterprise 27 绿（+4）、one-billing 24 绿（+2，含"公司未配置
任何 allowlist/预算时 pending 依然被拒"这条最关键的回归测试）。「去掉守卫」
负向验证：确认摘掉 `has_active_seat` 检查后，那条回归测试确实会红。

**隔离实例真实二进制端到端**（`--local --data-dir <tmp>`，用完即删）：把
`system_default_user` 自己的席位直接改成 `pending`（公司刻意**不配置**任何
allowlist/预算——原缺陷放行一切的那个最坏场景）→
`POST /api/one/billing/media-precheck` 返回 `{"allow":false,"reason":"...
Seat limit reached for the current plan"}`；`GET .../company/members` 的
`seatStatus` 正确显示 `pending`；`GET /api/one/billing/plan` 的 `seatUsed`
从 1 降到 0（不再把 pending 算进已用席位）、`seatPending` 从 0 变成 1。
改回 `active` 后，同一用户的 media-precheck 立即变回 `{"allow":true}`，
`seatUsed`/`seatPending` 同步复原。

## 六-5、T7 部门预算 / 成本分摊（2026-08-09 落地）

公司级成本上限（P1-2）只有一个数字，管理层拿到账单后第一个问题永远是
"哪个部门花的"——T6-3 已经把部门树接进项目组，这一项是把它接进计费面。

### 设计：写入时打标签，不是查询时现算

`one_usage_events` 新增 `department_id` 列，在 `record_turn`/
`record_media_usage` 落库那一刻从 `one_user_org.department_id`
读一次并直接写死，**不是**在报表/账单读取时临时 JOIN 现算。

理由：部门是一个**成本归属单位**。如果改成查询时现算，某人年中从"研发部"
调到"市场部"，会让他上半年的全部历史花费瞬间从研发部的账上消失、出现在
市场部账上——财务对账时账对不上，且没有人能解释为什么。写入时打标签，
调岗只影响**从那一刻起**的新支出，历史一笔不动。

跨 crate 读取沿用 `resolve_enterprise_id` 已有的裸 SQL 惯用法（one-billing
不依赖 one-org），并用双层 `Option`（外层"该用户有没有组织行"、内层"部门
字段本身是否为空"）避免把两种不同的"没有"语义混在一起。

### 分层关系：部门上限是公司上限之下更紧的一道闸

`check_send_allowed` 里部门检查**排在公司级预算检查之后**——先看公司整体
有没有超，再看这个人所在部门有没有超，两道闸都要过。`check_media_allowed`
直接委托 `check_send_allowed`，自动获得同样的保护（同 T4/T6-4 的既有模式）。
`DepartmentBudgetExceeded` 是独立的拒绝码（区别于公司级 `BUDGET_EXCEEDED`），
前端据此给出不同的文案——"等预算窗口"和"找部门管理员"是不同的建议。

### 落地内容

后端（one-billing）：迁移 `billing_004_department_budgets`
（`one_usage_events.department_id` + 新表 `one_department_budgets`）；
`set_department_budget`/`list_department_budgets`（管理员）；
`usage_summary` 新增 `by_department` 桶（复用既有 `buckets()` 聚合助手，
key 用 `COALESCE(department_id, 'unassigned')`）；两个新路由
`PUT`/`GET /api/one/billing/department-budgets`，与既有 `model-control`
同一套 `is_billing_admin` 门控。`aionui-app` 的 `billing_denial()` 新增
`DEPARTMENT_BUDGET_EXCEEDED` 映射分支。

前端（1oneUI）：`BillingTab.tsx` 新增「部门预算」卡片（表格逐部门设上限、
清空=取消部门级限制），用量看板加「按部门」桶；部门名称由计费面之外的
`oneAdmin.listDepartments`（项目组已有的部门树接口）在前端 join，
计费面本身对部门 id 保持不透明（同 `DepartmentBudgetDto` 的既有设计原则，
`one-billing` 不依赖 `one-org`）；`policyDenialError.ts` 新增拒绝文案；
13 语言 i18n。

**测试**：one-billing 新增 5 条（写入时打标签/调岗不影响历史/公司预算未
配置时部门上限独立生效/清空上限恢复放行/列表聚合），负向验证——去掉部门
检查后确认独立生效那条测试真的会红。前端新增 3 条（无部门=不渲染卡片、

## 六-6、T8 生成物集中账本（2026-08-09 落地）

补完"AI 员工"叙事的最后一块：员工每天用它生成图片/视频，但事后没人能回答
"这张图是谁生成的、在哪个会话、文件在哪"——`one_usage_events`（T7 之前唯一
的媒体记录）只管花了多少钱，压根不记文件路径，`list_agent_audit` 只看得到
agent 工具调用发起的那一条路径（发送框直接生成的那条路径不写任何消息，
完全不可见）。

### 设计：新增独立账本，不改既有计费路径

新表 `one_media_assets`——**一个生成的文件一条记录**（一个任务产出 4 张图
就是 4 条，而不是任务粒度的聚合），字段含 `user_id`/`department_id`（复用
T7 的部门解析）/`conversation_id`/`kind`/`model`/`file_path`/`prompt`/
`created_at`。刻意**加法式接入**：`reportMediaAsset()` 是在既有
`reportMediaUsage()`（计费）调用之后**追加**的独立上报，不改动、不依赖
后者，两条路径各自失败互不影响——账本记录失败绝不能让花费上报也跟着失败。

同企业作用域红线：个人/无企业用户的生成不写任何账本行（真机验证过：
移除企业成员关系后上报静默返回，表里 0 行）。

### 提示词留存：默认关闭，服务端强制，绝不信任客户端

`record_media_asset` 的 `prompt` 参数客户端**总是如实发送**（是否记录是
公司的内容留存决策，不该由客户端自己悄悄决定"不发"），但服务端按公司
`one_media_ledger_settings.retain_prompts`（默认 `false`）决定是否真的
落库——即使客户端传了完整提示词，未开启留存的公司这一列永远是 NULL。
真机验证过**追溯不生效**这个关键不变量：先按默认设置写入一条（prompt=null）
→ 管理员开启留存 → 再写入一条（prompt 正确落库）→ **第一条的 prompt 依然是
null**，开关不会重写历史。同理，提示词检索（`promptContains`）对未留存的
公司天然找不到任何结果——列本身是 NULL，`LIKE` 匹配不到，不需要额外判断。

### 进备份：账本本身，不是文件本体

`one-org/src/backup.rs` 的 `BACKUP_TABLES` 新增这两张表——注意这**不同于**
既有排除在外的 `one_usage_events`（那是无界的事件遥测，故意不进备份）：
账本是产物本身**唯一留存的痕迹**，丢了等于产物凭空消失。⚠️ **只备份路径和
元数据，不备份文件本体**——`backup.rs` 是纯 DB 行 JSON 导出机制，从来没有
处理文件 blob 的能力，磁盘上的实际图片/视频不在这次改动范围内。真机验证：
`GET /api/one/admin/backup/export`（`RequireSystemAdmin`）导出的 bundle
里确认能看到 `one_media_assets`（3 行，含未留存/已留存两种状态）和
`one_media_ledger_settings`（1 行）。

### 落地内容

后端（one-billing）：迁移 `billing_005_media_ledger`；
`record_media_asset`/`list_media_assets`（管理员搜索，按
kind/model/user/since/promptContains 过滤，limit 夹在 [1,1000]）/
`set_media_ledger_retain_prompts`；三个新路由——`POST
/api/one/billing/media-ledger/report`（任意成员均可上报自己的生成，同
`/media-usage` 权限模型）、`GET .../media-ledger`（管理员搜索）、
`GET`/`PUT .../media-ledger/settings`（管理员开关）。one-org：
`backup.rs` 的 `BACKUP_TABLES` 加两张新表。

前端（1oneUI）：`mediaJob/governance.ts` 新增 `reportMediaAsset()`，
`mediaJob/index.ts` 的 `reportJobUsage()` 在既有花费上报之后按
`job.assets` 逐个追加账本上报（同一批任务产出的每个文件独立一条）；企业后台

13 语言 i18n。

**测试**：one-billing 新增 3 条（个人用户静默跳过/默认不留存+开启后才留存 +部门正确挂载/检索过滤含"未留存公司搜提示词天然为空"）、one-org 51 条全绿

## 六-7、T1 真正的服务端交付（2026-08-10 落地，方案见下）

调研发现现状比预想的好得多：**不是从零架构，是补齐+打包**。`aioncore` 本身
对 Electron 没有硬依赖（可选 `--parent-pid`、真实优雅关闭、`/health`、
启动自动迁移、完整多用户 JWT），`1oneUI/packages/web-cli`（`aionui-web`
二进制）早就是一个零 Electron 依赖的独立 web 运行时——"后端脱离 Electron +
浏览器可访问"这条链路本身已经存在且被 CI（`pack-web-cli.yml`）验证过，
只是没被当成正式交付物包装成 Docker 镜像、写进部署文档。真正坏的只有
`1oneUI/Dockerfile`（引用的构建脚本两个月前就被删除，从加进仓库那天起就
没构建成功过，CI 也从未跑过 `docker build`）和 `docs/guides/deploy-server.md`
（部署的是整个 Electron 桌面壳 + Xvfb，不是 `aioncore` 自己）。

**方案范围**（完整方案见 `.claude/plans/snazzy-bubbling-frost.md`）：
把单实例部署做扎实，**不是**把架构改成水平扩展的多租户 SaaS——那是完全
不同量级的项目（换数据层到 Postgres、分布式限流、对象存储……），
`crates/aionui-app/src/main.rs` 的 `DataDirInstanceGuard` 决定了当前数据层
（SQLite 单文件）从设计上就没打算支持多副本。

### 阶段一：`aioncore` 运维硬化（1oneCore，已提交并真机验证）

`--host`/`--port`/`--data-dir`/`--log-dir`/`--log-level` 全部支持
`AIONUI_*` 环境变量回退（容器编排靠环境变量注入配置，不用再拼 entrypoint
脚本传 argv）；新增 `AIONUI_LOG_JSON=1` 让 stdout 控制台层也输出 JSON，
方便容器日志采集直接解析结构化字段。**首次管理员账号沿用已有的
`resetpass` 子命令，没有新造 HTTP 引导接口**——真机验证发现它比预想的
还好用：在一个全新的空 `--data-dir` 上直接跑 `resetpass`（不需要先启动
一次服务器）就能建好 schema、seed 默认用户、重置密码，一步到位。

### 阶段二：Docker 镜像 + 部署产物（1oneUI，已提交）

新 `Dockerfile`（整个替换掉坏的那个）：直接打包 CI 已产出、已 smoke test
过的 `aionui-web` tarball，不在镜像构建过程里重新编译 Rust/TypeScript；
新增 `docker-compose.yml`（含可选 Caddy sidecar 自动签发 HTTPS 证书）；
`pack-web-cli.yml` 新增 `smoke-test-docker` job（`docker build` + 起容器

- 验证 `/api/auth/status` 健康检查 + 首次密码登录闭环 + `docker exec`
  跑 `resetpass`），补上旧 Dockerfile "从来没被 CI 碰过所以没人发现坏了"
  的那个漏洞。

**顺带核实了一处容易看错的安全设计**：`aioncore` 内部总是以 `--local`
被拉起（字面意思像"跳过鉴权"），但反向代理会给每个转发请求打
`x-aionui-forwarded-origin: webui` 头，鉴权中间件看到这个头时**不会**走
自动登录捷径而是走完整 JWT 校验——"自动登录"只对完全绕开代理、直连
`aioncore` 回环端口的请求生效，而那个端口从不对容器外暴露。即
Docker 部署下每个用户仍必须用真实账号登录，不存在"整个部署共享一个免

### ⚠️ 补充（2026-08-10）：这条记的是"AIGC 标识"，不是"水印"，两者是两回事

用户反馈"水印功能开着关不掉，出海东南亚不需要"——查完发现和上面这条容易混但根本不是一回事：

- **AIGC 标识**（本节讨论的）：显式标注"这是 AI 生成的"，中国监管要求，产品刻意不做。
- **水印**（用户实际问的）：厂商自己的装饰性/防盗用水印，和合规无关。**查了 `common/media/` 下全部生成驱动**——图片走的 `seedream` 网关是唯一一处显式传水印参数的，而且是**硬编码 `watermark: false`（关的）**；其余六个视频驱动（ark/dashscope/kling/cogvideox/openaiVideo/seedanceGateway）**压根不传任何水印相关参数**，生成结果带不带水印完全由各家网关自己的默认策略决定，不受本产品控制。

**结论**：不存在"关掉水印的开关"，因为水印从来不是被我们代码"打开"的。真要做到"部署到东南亚统一无水印"，得给另外六个驱动分别加水印控制参数——**但每家的参数名字、是否支持这个能力，需要真实 API 文档或抓包才能确认**（`AGENTS.md` 铁律：不能靠猜给外部 API 传参，猜错的参数名不会报错，只会静默不生效）。

**待办**：需要能拿到 ark/dashscope/kling/cogvideox/openaiVideo/seedanceGateway 六家真实 API 文档或密钥的人核实各自的水印控制参数，再逐个加。在此之前**不要凭猜测给任何驱动加 `no_watermark`/`watermark: false` 之类的参数**——加了测不出对错，等于没加还占了一条"已修复"的假记录。

### ✅ 更正 + 已修复（2026-08-10 续）：上面"结论"里"没有可关的开关"这句话是错的，图片这条路真的能关

用户拿真机截图指出"这个水印很明显是企业版改造之后才有的，之前我确定并没有"——顺着这条线索复查，发现和当天早些时候记的结论不一样：**图片这条路（`seedream` 家族）不是"从来没传过水印参数"，是"传了、但接错了线"**。

- `openaiImagesAdapter.ts` 里其实一直有两条路：`ark-seedream`（目录默认，直连火山方舟官方 API，走最通用的 `images/generations`，**不带任何水印字段**）和 `seedream-gateway`（专门给公司内部网关代理用，路由在 `/api/seedream/v1/`，**已经带 `watermark: false`，且注释写明是抓真实请求验证过的**）。这两条路是否走对，取决于 `catalog/imageModels.ts` 里 `ark-seedream` 目录条目有没有设 `endpointStyle`——它一直没设，所以**默认（自动识别）情况下，`watermark: false` 那条代码从来没被触发过**，走的一直是没有水印控制的直连分支。
- 这不是"猜参数名"，`watermark: false` 这个字段名早就在代码里、早就被验证过——只是没接到默认路径上。**这也不是需要外部 API 文档才能解的问题**：给 `ark-seedream` 这一个目录条目也补上 `watermark: false`（`openaiImagesAdapter.ts`），真机对比生成结果——角标从清晰可见的实心徽章变成几乎看不出的残影，改动生效。已提交 `189b243c4`。
- ⚠️ **这次真机测试过程中还顺手确认了一件事**：`seedream-gateway` 这条路的 host 是"公司自己开的内部网关"，跟官方直连地址（`ark.cn-beijing.volces.com`）完全是两个不同的服务器——手误把一个直连方舟的模型的接口协议设成 `seedream-gateway` 会打到一个不存在的路由上，秒级返回裸 `404`，界面上原来只有一句天书文案。顺带把这类"协议选错了但看不出来"的坑也堵了一版：接口协议下拉框从裸 id 换成人话标签、对能算出预期 host 的协议做非阻塞错配提示、失败卡片新增"去修改模型设置"直达入口（都是软提示不拦保存，跟本节"别猜参数"的铁律同一个精神）。已提交 `95a885ac7`。真机 CDP 全链路验证过（切错协议 → 提示出现 → 保存 → 触发真实 404 → 失败卡片给出建议+直达按钮 → 点击后正确跳转定位）。

**待办没变的部分**：`ark-seedream` 之外的六个驱动（ark/dashscope/kling/cogvideox/openaiVideo/seedanceGateway 的**视频**任务接口）依然是"压根不传水印参数"，依然需要真实 API 文档或抓包才能确认各家参数名——**这条铁律仍然成立，不要凭猜测加**。今天解决的只是图片这一条路，而且是因为参数名和验证依据早就在代码里，不是新猜的。
