# 2026-09-15：会话导入导出、媒体路由、本地 OCR、Agnes 四连修

本轮起点是用户提的三个问题，收尾时变成了四类修复。贯穿全场只有一条教训：
**把「文档怎么写」或「代码怎么设计」当成「线上怎么跑」，代价是整块功能静默失效。**
下面每一节都给了实测对照，没实测的地方会明写「未验证」。

---

## 1. 会话导入导出（换机器不用从零开始）

导出按类别勾选：会话+消息 / 附件 / 模型配置 / 技能。实现要点：

- **导出是真删，不是过滤。** 先 `VACUUM INTO` 出一份一致快照，再把用户没勾的表
  真正 `DELETE` 掉。只在读取时过滤等于把数据仍然装进了文件里——用户勾掉"模型配置"
  是因为里面有 API Key，不能只是不显示。
- **恢复是合并，不是替换。** 目标机器上已有的会话必须留下。
- 附件默认**不勾**：开发机上是 13,304 个文件 / 228 MB，要跑半小时，而其余类别几秒就完；
  默认勾上会让普通备份看起来像卡死。换机器需要的东西（会话、消息、模型、技能）都在 catalog 里。
- 备份完成后给一个**打开所在目录**的按钮。原来用户在原生对话框里选完路径、等完、看到一个
  toast，然后得自己回想文件放哪了。

### 真实 bug：`ATTACH DATABASE` 是连接级状态，不是库级

恢复在生产环境稳定 500，而全部单测是绿的。原因是合并逻辑从连接池里**每次取一条新连接**：

```rust
// 错的：ATTACH 在连接 A，后面的 SELECT 落到连接 B
sqlx::query("ATTACH DATABASE '...' AS backup").execute(pool).await?;
merge_tables(pool).await?;   // no such table: backup.sqlite_master
```

必须整段跑在**同一条**取出来的连接上：

```rust
let mut conn = live.acquire().await?;
sqlx::query(&format!("ATTACH DATABASE '{staged}' AS backup")).execute(&mut *conn).await?;
let result = merge_tables(&mut conn, scope).await;
let _ = sqlx::query("DETACH DATABASE backup").execute(&mut *conn).await;
```

**测试为什么没抓到**：测试池是 `max_connections(1)`，生产是 `5`。一条连接的池子里
"每次取新连接"和"复用同一条"看不出区别。把测试池调成和生产一样的 5 之后，回滚修复
能稳定复现出 5 个失败、报的正是生产那句 `no such table: backup.sqlite_master`。
`PRAGMA foreign_keys` 同理，`prune_catalog_to_scope` 里是同一个形状。

> 规则：**连接池大小是被测行为的一部分**。测试池和生产池不一致时，整类连接级状态 bug 会被
> 悄悄掩盖掉。

## 2. 媒体路由：有图片/视频模型却用文本模型画图

两个独立缺口：

1. 会话里没有快速路由到图片/视频模型的入口——用户装了生图模型，发"画一只猫"仍然走文本模型。
   新增 `detectMediaIntent`，中文强动词用了负向断言避免误伤：
   `/(?<![动漫计图书刻])(画|绘制)(?![面布廊质风家笔展])/`——"动画""计划""画面""画风"都不该触发。
   视频先于图片判定。另加 ANALYSIS / CODE_CONTEXT 排除，"帮我分析这张图"不算生成。
2. **生图模式下生成完想改图，退回成了文本模型。** 欢迎页和输入框各自 new 了一个
   `useMediaComposer`，欢迎页那个 key 在"还没有会话"上，导航时被卸载；输入框那个挂载即 `off`。
   原注释写着输入框"自己有 state 会接上"——它没有那个 state。改成通过已有的请求通道把
   mode 和已解析的模型一起交给新会话。

## 3. 本地 OCR 只给纯文本模型

原本实现成"所有模型先走本地 OCR"，被用户纠正：**模型自己是多模态的，就该用它自己的眼睛**，
OCR 只是纯文本模型的兜底。

同时把 OCR 的措辞改实了。之前写的是"精确转写"，实测不是：

| 原文            | 本地 OCR 结果           |
| --------------- | ----------------------- |
| `INV-2026-0042` | `工 NV 一 2926 一 9942` |
| `CS1002`        | `CS1992`                |

中文环境下的本地 OCR 认错英文和数字是常态，结果文案现在明说这一点，并加了钉死测试。
**OCR 省的是钱，不是准确率。**

## 4. Agnes：四个 bug，互相掩盖

这一节是本轮最贵的。四个 bug 分属四个层，任何一个不修，上层的修复都不生效。

### 4.1 图生图：参考图必须放 `extra_body.image`

报错是：

```
400 BadRequestError: LLM Provider NOT provided. You passed model=agnes-image-2.5-flash
```

这句话**只提 model，完全不提 image**，而且同 key 同路由上文生图一直正常——所有信号都指向
凭据或路由。实测对照（同 prompt 同 key，只改放置位置）：

| 请求                      | 结果                                                           |
| ------------------------- | -------------------------------------------------------------- |
| `image` 放顶层            | 400 `LLM Provider NOT provided`                                |
| `image` 放 `extra_body`   | 200，正常返回图片                                              |
| `extra_body` 里放无效 URL | 400 `image must be a public http(s) URL or valid image base64` |

第三行是关键旁证：进了 `extra_body` 服务端才开始校验图片内容，证明字段被读到了。

> **官方文档的参数表把 `image` 和 `model`/`prompt` 并排列，看着像顶层参数；同一页的 curl
> 示例把它嵌在 `extra_body` 里。示例才是服务端的样子——表格表达不了嵌套。**

### 4.2 catalog 只认 `agnes-ai.com`，用户配的是 `agnes-ai.cn`

Agnes 同一套 API 有两个域名，而**一个 key 只被其中一个认**。实测同一个请求体：

| Host                  | 结果                                          |
| --------------------- | --------------------------------------------- |
| `apihub.agnes-ai.com` | 401 `Invalid token`                           |
| `api.agnes-ai.cn`     | 200 `{"video_id":"task_…","status":"queued"}` |

所以国内账号只能配 `.cn`，而三条 Agnes catalog 条目全都写死 `baseUrlIncludes: ['agnes-ai.com']`，
于是**一条都匹配不上**：

- 视频 resolve 成 null → 视频刻意不猜协议 → 模型直接从选择器里消失；
- 图片落回通用 OpenAI 条目 → 发出 Agnes 四处不兼容的请求体，**包括 4.1 刚修好的顶层 `image`**。

> 这是本轮最值得记住的一条：**所有厂商专属的请求整形都在 resolve 的下游。catalog 不认识这个
> host，等于把该厂商的全部修复静默关掉。** 4.1 修完当天其实对这个用户一行都没生效。

主机列表收敛到 `catalog/agnesHosts.ts` 一处，匹配的是可注册域名（子域 `api.` / `apihub.` 自动覆盖）。

### 4.3 视频驱动写死主机 + `mode` 与素材不匹配

驱动原来完全无视 `base_url`，永远打 `apihub.agnes-ai.com`——即使 4.2 修好让模型能出现在选择器里，
国内账号也还是 401。原注释的理由是"文档只印了一个 host，没有区域变体"，两半都是错的。
现在用用户配置的 host；原注释担心的"中转网关被绕过、把网关的 key 发给厂商"由上一层解决：
`baseUrlIncludes` 保证非 Agnes 主机根本 resolve 不到这个驱动。

然后是 `mode`。它不是标签，是**白名单**——每个 mode 会拒收其它 mode 的素材字段。实测：

| 请求                              | 结果                                              |
| --------------------------------- | ------------------------------------------------- |
| `mode=text` + `first_frame`       | 400 `text 模式不能包含素材字段`                   |
| `mode=keyframe` 不带任何帧        | 400 `keyframe 模式需要 first_frame 或 last_frame` |
| `mode=reference` + `images:[url]` | 200 queued                                        |

原驱动把素材压成一个值（`firstFrameImage || inputs[0]`）、只发 `first_frame`，于是两样东西
无声消失：用户选的**尾帧**，以及第一张之后的**所有附件**。现在按手里实际有什么来选 mode：
显式首/尾帧 → keyframe（两个都发）；单张附件 → keyframe（保持原有的"图生视频"语义）；
多张附件 → reference（`images`，按文档上限截到 5 张，超限会整条请求被拒）。

配套：catalog 2.5 条目补上 `firstLastFrame: true`，否则 `clipParamsToSpec` 在到达驱动前就把
`lastFrameImage` 丢了——**和当初 Seedance 视频没声音是同一个静默丢字段的形状**。

### 4.4 `agnes-3.0-flash` 会看图，但我们从不让它看

它不在后端 `image_input_models.json` 白名单里 → 解析成 `Unknown` → 附件被转交给
**视觉代理模型或本地 OCR**。用户自己的多模态模型闲着，让另一个模型、或一个会认错字符的 OCR
去回答它本可以自己回答的问题——正好是第 3 节用户明确要求不要发生的事。

实测（两种我们的管线会产生的 `image_url.url` 写法，都准确描述了图片内容）：

| 写法                      | 结果 |
| ------------------------- | ---- |
| `https://` URL            | 200  |
| `data:image/png;base64,…` | 200  |

**第二行必须实测。** 模型页把输入模态写成"文本、图像 URL"，唯一的示例也传 URL，
而我们发的每个本地文件都是 data URI。照文档字面理解就会为一个服务端根本没有的限制
把这条白名单扣下——和 4.1 的方向正好相反：**同一家厂商的文字说明，一处比实际严、一处比实际松。**

白名单里只加了 `agnes-3.0-flash`，因为只测了它。

## 附：这一轮我被用户纠正的地方

记下来是因为它们都是同一个毛病——**把推测当结论输出**：

1. 从错误信息格式猜"Agnes 网关是 litellm 搭的"。不是。
2. 据此断言"不是我们的代码问题，是 Agnes 服务端坏了"。是我们的代码问题。
3. 拿 30 秒采样的 89 KB/s 外推成"还要 30 分钟"，建议用户取消备份。实际 6 分钟就完了。
4. 用 JS 注入冒充 CDP 点击。真实 `Input.dispatchMouseEvent` 点下去才发现"系统"菜单
   （y=703–737）在 720px 视口里被切掉了——JS 注入永远发现不了这个。
5. 在用户已经起了 dev 的情况下又起一个，然后按路径批量杀 electron，把用户那个也杀了。

> 对应的长期规则：**该自己定的技术方案不要推给用户，但没验证过的结论更不能直接断言。**
