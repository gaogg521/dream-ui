# 2026-09-19：备份恢复在别的机器上必挂，以及给备份包加密

涉及两个仓库：**dream-core**（备份服务、加密）、**dream-ui**（密码对话框）。

用户报的是一个现象：「会话备份导出后，在其他机器恢复有问题」，界面上只有一行
`Backend POST /api/system/backup/restore failed (500): INTERNAL_ERROR`。

查下来是**两个独立的 bug**，加上用户提的**一个安全改进**。

---

## 1. 500 的根因：外键顺序，不是加密也不是路径

`merge_tables` 按**类别顺序**逐表插入，而那个顺序**不是拓扑序**：

| 表                                  | 属于     | 插入次序 |
| ----------------------------------- | -------- | -------- |
| `conversation_assistant_snapshots`  | 会话     | 第 4     |
| `assistant_definitions`（它引用的） | 助理设置 | **最后** |

真实 schema 有 **28 条外键**，实库上 `foreign_keys` 是**开着**的
（`dream-core-db/src/database.rs` 两处 `.foreign_keys(true)`）。

**在导出的那台机器上父行本来就在**，所以永远不报错。换台机器就还没有 →
`FOREIGN KEY constraint failed` → `SystemError::Internal` → 500。

> 这个 bug 只在「本功能存在的唯一目的」——换机器——上触发，其余场景全部正常。

### 导出路径早就关掉了外键，合并路径没关

`prune_catalog_to_scope` 里写着 `PRAGMA foreign_keys=OFF` 并附了注释说明原因
（`users` 的级联会删掉 scope 想保留的行）。**同一份代码里，同一个理由，合并路径漏了。**

### 修法与两个必须注意的位置

1. **`PRAGMA foreign_keys` 必须在 `BEGIN` 之前** —— 它在事务内是**文档化的 no-op**，
   写在 BEGIN 之后会静默不生效。
2. **连接还回池子之前必须改回 ON** —— 否则之后所有走到这条连接的查询都不校验外键。

### 顺带修掉：恢复不是原子的

失败前已经 commit 的表就留在目标机上了。拿用户真实的 17 MB 备份包实测：

|        | 表     | 行       | 目标机剩下什么                           |
| ------ | ------ | -------- | ---------------------------------------- |
| 修复前 | 3      | 2341     | 会话 43、消息 2297，**服务商 0、技能 0** |
| 修复后 | **27** | **3884** | 完整                                     |

现在整个合并 + 清理在一个事务里，失败回滚。

### 部分恢复会留下孤儿，现在清理并**报告**

只勾「会话」不勾「助理设置」是**支持的选择**，结果是 `conversation_assistant_snapshots`
指向从未到达的定义（实测 20 条）。现在合并后跑 `PRAGMA foreign_key_check` 把这些删掉、
计数返回给前端，界面显示为**警告**而不是「已恢复 N 条」—— 否则部分恢复看起来是无损的。

### 我自己在这轮犯了两次同一个错

改了 `runBackendMigrations.ts` 却只跑 `tests/unit/webSearch`，漏了
`tests/unit/bootstrap`；改了 `BackupSection.tsx` 却只跑 tsc/i18n，漏了
`BackupSection.dom.test.tsx`。两次都是 pre-push 钩子拦下来的。

**改哪个文件，就去找哪个文件的测试** —— 不要按功能名去猜测试目录。

### 为什么原来的测试抓不到

`backup_test.rs` 的 fixture 是手写的玩具 schema，**一条外键都没有**。文件开头的注释
自己写着「mirror the real schema's shape **where that shape matters**」——
而真正要命的那个 shape 恰好没有。现在 fixture 声明了外键，新增 3 个测试，
并**反向验证过**（去掉守卫 → 红）。

## 2. 更隐蔽的一个：恢复会换掉本机的加密密钥

`providers.api_key_encrypted` 用 `derive_encryption_key(users.data_secret)` 加密，
而 `data_secret` **在启动时读进内存**（`services.rs` 的 `data_secret_raw`），此后不再读。

恢复时 `users` 走 `OR REPLACE`（TEXT 主键，非代理键）→ **备份里的 `data_secret`
覆盖了本机的**。核对过用户的备份包和一台目标机（只比对布尔、不读密钥值）：
**用户 id 相同、`data_secret` 不同**。于是：

- 进程手里还是旧密钥 → **恢复过来的模型密钥当场解不开**，必须重启
- 重启后换成备份的密钥 → 恢复的能用了，但**目标机原有的模型密钥全部永久解不开**

模块文档里写着「恢复不需要重启」—— 对服务商密钥来说是错的。

**修法**：本机密钥**保留**，备份的密钥只用来**读**备份带来的东西，读出来立刻用本机密钥
重新加密。两边都不用重启、都不会坏。解不开的行**原样保留**而不是清空 —— 那是源机器
轮换过密钥的情况，清空会把「不可用的凭据」变成「丢失的凭据」。

## 3. 用户提的：备份包本身要加密

> 「导出的时候应该设置一个密码，导入的新主机应该输入密码后才能导入」

对，而且用户那个包的 manifest 自己写着 `containsCredentials: true` ——
**17 MB 明文 zip 躺在桌面上，里面是可直接用的 API 密钥**。

| 决定      | 选择                                                           | 理由                                                                                            |
| --------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 加密范围  | `catalog.db` + `files/`，**`manifest.json` 明文**              | 清单里只有日期/版本/类别，没什么好藏；留明文才能**不输密码就看到包里有什么**                    |
| 口令      | **强制**                                                       | 每个包都带 `users.jwt_secret`，没有「这个不敏感」的档位                                         |
| KDF       | **Argon2id**（64 MiB / 3 轮 / 每包独立 salt），新依赖 `argon2` | 现成的 `derive_encryption_key` 是裸 SHA-256 —— 对机器生成的高熵密钥够用，对人选的口令等于不设防 |
| 密码错误  | header 里放一个**验证器**                                      | 否则要等几 MB 之后在 catalog 上炸，用户会以为文件坏了                                           |
| 格式版本  | 2 → **3**                                                      | 旧客户端明确拒绝，而不是解出一堆密文再报「数据库损坏」                                          |
| 旧包      | 继续能恢复（无 `encryption` 字段 = 明文）                      |                                                                                                 |
| 逐条 seal | 不是整包加密                                                   | 峰值内存 = 最大单文件；实测有过 13,304 文件 / 228 MB 的导出                                     |

`ArchiveKey` **手写脱敏 `Debug`**，不是 derive —— derive 会把密钥打进任何格式化输出。

## 4. 真机验证（真二进制 + 真 HTTP 接口 + 两台"机器"）

不是单测，是起两个 `dreamcore --local` 实例、各自独立 data-dir 走完整流程：

| 步骤               | 结果                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| A 机导出           | 200，4.2 MB，`formatVersion: 3`                                                         |
| **加密是否真生效** | catalog 首字节 `72 91 00 53…`，**不是 SQLite 文件**；`END TO END TEST` 在包里**搜不到** |
| 不输密码预览       | 200，能看到日期/版本/类别/是否含凭据                                                    |
| B 机**错**密码     | **400「That passphrase does not open this backup」**，且**什么都没写进去**              |
| B 机对密码         | 200，7 表 355 行，会话到位，技能 27，**外键违规 0**                                     |

> 第二行是关键：**只测「对密码能开」的话，加密没生效也一样绿。**

### 一个需要如实说明的行为

全选恢复清掉了 5 条 `assistant_overlays` 孤儿。查到底不是 bug：
`assistant_definitions` 有 `(user_id, assistant_id)` 唯一索引，两台机器首启都种了同样
26 个内置助理（`assistant_id` 相同、行 id 不同），A 的定义按唯一索引**替换**了 B 的，
B 自己那 5 条 overlay 指向被替换掉的行 id 就成了孤儿。最终 **B 的定义集合与 A 完全一致**
—— 正是「换机器带走」该有的结果。**而且它被报告了**。
